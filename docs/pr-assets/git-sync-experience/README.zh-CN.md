# Git 同步：操作体验与边界情况

[English](./README.md) | [验证记录](./verification.json)

Git 同步在 v0.5.26 发布时，所有控件挤在一张长表单里：操作按钮排在它们依赖的配置之前，还没有仓库就先出现自动备份，四个地址字段并排，访问令牌下面有三行说明，同一次读取既有预览条又有弹窗，两个按钮做同一次合并，失败时直接显示 Git 的原文。这次改动按使用顺序重建这一块：先连接仓库，再同步，同步前可以检查会发生什么，最后才是高级选项。实际跑这些流程时还发现了 Host 里的几个边界问题，其中最严重的一个会把一个仓库的历史发布到另一个仓库。

基线：`main` `1a6ff881`（v0.5.27）。本次改动：分支 `claude/git-sync-ux`，提交 `e2ff299e`（Host）、`6700da70`（页面）、`415a7441`（文档）、`78769ec6`（令牌主机）、`fcea8525`（打开 GitHub、向空分支第一次同步、断开时关闭定时）、`95bd46c4`（下文的评审修正）与 `8a73ab09`（这台电脑的名称）。运行于 2026-10-11（Asia/Shanghai）：
- macOS 15.6 arm64、Node 24.19.0、Git 2.50.1；
- 无头 Chrome 154，1280×1000，浅色，zh-CN 与 en-US；
- WebUI 使用 DSH 0.2.0-rc.2（npm `latest` 与 `next`）；端到端通道检查另外覆盖 0.2.1-alpha.2 与固定基线 0.1.7-rc.2；
- 两个 WebUI 实例模拟两台电脑，分别命名为 “MacBook” 与 “Studio”，通过同一个裸仓库同步。只交给这两个实例的 Git 配置（`GIT_CONFIG_GLOBAL`）把地址 `https://git.example.com/demo/memory.git` 映射到这个仓库，因此截图里显示的是普通的 HTTPS 地址。

## 页面上的变化

| | v0.5.27 | 本次改动 |
|---|---|---|
| 顺序 | 先是推送、检查远端、备份历史，然后在一张表单里依次是 GitHub、自动备份、仓库选择与地址字段 | 一张卡片，按设置的先后排列：仓库、同步、自动同步、备份历史、高级设置 |
| 连接 | GitHub 区块、仓库选择区块与四个地址字段并列；保存按钮置灰却不说明原因 | **GitHub 账号**或**仓库地址**。一次点击即复制设备码并打开 GitHub；登录后可以搜索仓库、用输入的名称新建私有仓库，选择公开仓库前先确认。地址在发送前检查，只有 HTTPS 地址才出现访问令牌一栏 |
| 状态 | 所有失败都显示“远端不可达 · 未保存凭据”，本地或 SSH 仓库也显示“未保存凭据” | 显示仓库、是否有响应与认证方式；失败时说明原因（凭据、找不到、网络、超时），需要时提供**设置凭据**；没有凭据的 HTTPS 仓库会在第一次推送失败之前就标注出来 |
| 同步 | **推送**（其实已经会先合并远端），以及**检查远端**之后的预览条上的**拉取并合并**和弹窗里的**直接新增**：同一次合并有两个按钮 | **立即同步**先合并再推送，这一行说明带来了什么以及上次同步的时间。**检查远端**比较各组件与运行时记忆条目，不写入任何内容，并提供**只合并到本机**与**立即同步** |
| 失败 | Git 的原文，例如 `fatal: could not read Username for 'https://github.com': terminal prompts disabled` | 页面的语言：“需要凭据，请用 GitHub 登录或填写访问令牌”；无法归类的才保留 Git 原文 |
| 自动同步 | 原生 `<select>`，选择即保存，而周围的字段要点保存 | DSH 选择器，并说明下次何时运行或上次为什么失败 |
| 历史 | “备份历史”与“检查远端”打开同一个弹窗，从检查远端打开时一直停在“读取中…” | 独立弹窗：时间、设备、各组件包含多少内容；只有人工写下的提交说明才显示 |
| 高级 | 分支、目录与提交者一直显示；提交者字段显示默认身份，提示却写“留空则使用本机 Git 身份” | 收在展开项里；每项显示当前使用的值，提交者是明确的选择：默认、本机 Git、自定义 |
| 电脑名称 | 历史与检查远端用标识生成时的主机名称呼每台电脑，固定写在 `state/machine.json` 里，只能手动改文件 | 高级设置里的**这台电脑的名称**：**主机名**跟随当前主机名，**自定义**保留输入的名称；下一次同步会发布它，之前的版本保留原名称 |
| 退出 | 无法移除仓库；“清除凭据”是一个保存时才生效的勾选框 | **断开**会先确认，本机与仓库里的内容都不删除，并关闭自动同步；已保存的令牌旁有**移除** |
| 记忆整理 | 常驻的三段“运行规则” | 去掉；每条后果在对应的位置说明 |

## Host 的边界情况

每一行都有对应的测试：在 `main` 上失败，在本次改动上通过（除另注明外均在 `tests/git-sync.spec.ts`）。

| 情况 | v0.5.27 | 本次改动 |
|---|---|---|
| 换到一个空仓库 | 镜像保留了第一个仓库的提交，于是第一次推送把整段历史发布到第二个仓库。已在 WebUI 中复现：向 A 推送后，空仓库 B 里出现了建立在 A 的 `0b70d12` 之上的 `214968c` | 镜像记录它取自哪个仓库（`mnemon.origin`），换仓库时重建；B 里只有一个根提交 |
| 为了重新开始而删除了远端分支 | 下一次推送会把之前所有的载荷重新发布 | 远端没有的分支从新的历史开始 |
| 另一台设备在本机 fetch 与 push 之间推送 | 只在本地提交，提示“推送未完成：[rejected] (fetch first)” | 再合并一次分支并重试推送一次；只有第二次仍被拒绝才报告 |
| Host 在操作中途停止 | 锁目录一直留着，之后每次同步都失败，提示 “another Mnemon sync operation is still running”，直到有人手动删除 | 锁记录持有者。持有进程已不存在的锁立即接管，旧版本留下的无记录锁 15 分钟后接管，任何锁超过一小时都会接管；接管前先把锁改名移开再删除，两个 Host 不会同时拿到它。遗留的单次命令凭据文件也会被清除 |
| 同一版本被合并两次，例如重试的同步（`tests/pack.spec.ts`） | 每个有分歧的项目档案或记忆空间都会以另一个新 id 再复制一份 | 按内容找到已经做过的副本，每处分歧只保留一份 |
| Git 2.20 到 2.27 | `git init --initial-branch` 需要 2.28，而通道声明只需 2.20，第一次同步就会失败 | 初始化镜像时不再使用这个选项 |
| 本机没有 Git 身份时提交者留空 | 提交失败，或发布 Git 根据账号与主机名猜出的身份 | 使用本机已配置的身份，否则使用通道自己的身份 |
| 为一个主机保存了令牌，又把仓库换到另一个主机（`78769ec6`） | 下一次状态探测与推送会把令牌交给新主机 | 除非随更换一起提供新令牌，旧令牌会被丢弃 |
| 主机丢包不响应 | 页面最多要等 120 秒才拿到状态 | 状态探测 20 秒后放弃，并提示“仓库没有及时响应” |
| 被拒绝的操作 | 只有 `code: internal` 与 Git 原文 | `details.reason` 给出类别（`remote-auth`、`remote-not-found`、`remote-network`、`remote-timeout`、`push-rejected`、`remote-empty`、`busy`、`no-repository`、`git-missing`、`github-unauthorized`），`scripts/verify-sync-git.mjs` 经由真实 DSH 检查 |
| 预览计数 | “0/3 个组件不同”旁边却是“不同 1”：重新盖了时间戳的 manifest 被计入 | 只计算载荷文件 |
| 收拢体积 | `git count-objects` 给出的 KiB 被当成字节显示（“52 B → 2 B”） | 换算为字节；页面也不再播报这项内部整理 |
| 推送时读两次远端 | 推送刚准备好镜像，`readRemote` 里又执行了一次 `ensureMirror` | 每次尝试只读一次 |
| 超过 100 个 GitHub 仓库 | 只列出第一页 | 最多读取五页，按最近更新排序，可在页面内搜索 |
| 在 github.com 上撤销了授权 | “GitHub 登录失败：listing GitHub repositories failed: Bad credentials” | “GitHub 授权已失效，请重新登录”，并提供**重新登录** |

## 评审

一次独立评审检查了前五个提交，发现了下面这些问题；`95bd46c4` 逐一修正，能测试的行为都补了测试。

- 状态探测从未真正使用 20 秒上限：`git()` 忽略了单次调用的超时，不响应的主机仍会让页面等 120 秒。
- 推送被拒绝后的重试会把远端再合并一次，给每个有分歧的项目档案或记忆空间多复制一份，而且只报告第二次尝试带来的内容。
- 无持有者记录的锁一分钟后就被接管，可能在旧版本 Host 慢速推送的中途夺走它的锁；两个 Host 也可能同时接管同一个过期锁。
- 自动同步失败的原因在错误消失后仍然保留；因另一次同步正在进行而跳过的同步也被算作失败。
- 比较时同时读取预览与文件差异，后一个可能撞上前一个的锁而失败。
- 比较的计数把待审核的条目与本机删除又算进了“只在远端”和“只在本机”。
- 从比较里发起的同步失败、以及断开失败，都只在弹窗背后显示。
- 不是 github.com 的 HTTPS 主机也被提示用 GitHub 登录；被 GitHub 报告为找不到的仓库没有设置凭据的入口。
- 一次轮询失败就会结束 GitHub 登录；其他账号下的同名仓库会挡住在自己账号下新建；历史没有说明最多只列出最近 100 个版本。
- 旧版本只保存了一个字段的提交者，会让高级设置里的其他修改都无法保存。
- 令牌的**移除**按钮放在字段标签里，本想点标签的一次点击可能把令牌移除。
- 指南写着远端不可达时仍会在本地提交（其实读取会先失败），没有说明 `MNEMON_SYNC_GIT_TOKEN` 优先于 GitHub 登录，并把历史写成没有上限。

## 测试

- Host：用本分支的测试跑 `main` 的 Host 源码，有 16 个用例失败，在本次改动上全部通过：`tests/git-sync.spec.ts` 中 13 个，`tests/pack.spec.ts`（第二次合并）、`tests/github-auth.spec.ts`（分页）与 `tests/sync-rpc.spec.ts`（经由 RPC 处理器返回的原因）各一个。完整列表见 [verification.json](./verification.json)。
- 这台电脑的名称：`tests/machine-identity.spec.ts`（跟随主机名、所有读取方都能看到的自定义名称、旧版本的记录、被拒绝的名称），以及 `tests/git-sync.spec.ts` 中的一个用例（状态里的名称、被拒绝的名称不影响同一请求的其他设置、发布出去的名称、改回主机名）。
- 页面：`tests/client-sync.spec.tsx`（30 个用例）用模拟 Host 驱动这一块：地址检查、令牌字段、同步结果、命名的失败、不写入的比较及其第一次同步、历史、一次点击的 GitHub 登录、公开仓库确认、新建仓库、失效授权、设置凭据入口、断开、高级表单与英文，评审在页面上的每一条发现各有一个用例，电脑名称另有两个。`tests/client-memory-enhancements.spec.tsx` 确认开关关闭时保持沉默。
- 端到端：`scripts/verify-sync-git.mjs` 用两个 DSH 实例与真实裸仓库，在 DSH 0.1.7-rc.2、0.2.0-rc.2 与 0.2.1-alpha.2 上都通过全部 64 项检查，其中 3 项检查电脑名称。
- `pnpm verify` 与 `verify:plugins`：见 [verification.json](./verification.json)。

## 局限

- 这些运行没有用真实账号完成 GitHub 登录。设备码流程、仓库列表与新建仓库由 `tests/github-auth.spec.ts` 与使用模拟 Host 的页面测试覆盖；截图展示的是地址方式。
- 只在 macOS 上运行，也没有检查 DSH 桌面版。
- 比较时运行时记忆仍按条目统计，另外两个组件仍只给出“一致”或“有差异”，与之前相同。
