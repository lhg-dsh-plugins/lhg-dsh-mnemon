# 合并之后每次同步都复制一份记忆空间 — issue #391

[English](./README.md) | [验证记录](./verification.json)

issue #391 发现点了**立即同步**之后多出一个存储：它是一个仍在使用的空间的完整子集，处于激活状态，还会代替原空间回答召回。issue 下的一条评论把原因追到 Git 同步对记忆空间的合并。Mnemon 的 `edges` 行以它连接的两条记忆及其类型为主键，但合并比较了所有列。一次本地的空间合并改写了主空间的每一条边（权重 0.5、新的备注、新的时间），而分支上保存的仍是发布时的样子。下一次合并试图把分支上的这些边作为新行插入，撞上主键，于是放弃合并，把分支上的版本保留为一个新空间。这个副本随后又被合并回去，循环往复：评论者的机器上累积了五个副本。

基线：main `4feee034`。修复：`4eaa205d`，审查修复在 `cc4272c1`。运行于 2026-10-17（Asia/Shanghai）：
- macOS 15.6 arm64，Node 24.19.0，Git 2.50.1，Mnemon CLI 0.2.10；
- 无头 Chrome，1280×800，zh-CN，浅色；
- DSH 0.2.1-alpha.2（npm `alpha`），通过 `scripts/serve-e2e.mjs --docs-demo` 运行；
- 同步远端是一个本机裸仓库。

## 原因

自 #370 起，合并逐行比较一个空间的两个版本所持有的内容，并加入只有对方持有的行。除用量列和向量之外，每一列都参与比较。有两类值不是用量，但 Mnemon 会在行的内容不变时重新写入它们：
- 边的 `weight`、`metadata` 与 `created_at`。`mnemon import` 会为它收到的每条边重新写入这些值，dsh-mnemon 自己的空间合并（`mnemon_memory_body_merge`）正是这样把源空间的记忆和边导入目标空间，权重 0.5，备注为边的类型。所以把某个空间的副本合并回它自己，会改写两者共有的每一条边的值。用真实 CLI 做的探针把一个存储导入它自身，12 条边的主键全都不变，值全部改变。
- 记忆的 `updated_at`。嵌入服务恢复响应后，`mnemon embed --all` 会在它补齐的每个向量上盖上这个时间，`mnemon gc --keep` 也会改写被保留的那条记忆的这个时间。审查发现了这第二种情况：同步之后补齐了向量的机器，同样无法合并已发布的版本。

## 修复

- 边的权重、备注和时间不再参与比较：一条边就是它连接的两条记忆及其类型，也就是它所在表的主键。合并时，两边都有的边保留本机的值；只有对方持有的记忆和边仍会加入。
- 记忆的更新时间也不再参与比较。编辑仍会改变记忆的内容，遗忘仍会写入 `deleted_at`，所以某条记忆在一边被编辑或遗忘时，仍像以前一样保留一份副本。
- 每张表要排除的值改用 `Map` 保存。之前的普通对象在遇到名为 `constructor` 的表时会返回 `Object` 本身，读取这样的空间会抛出异常，退回按字节比较。

## 方法

1. `pnpm e2e:serve --docs-demo` 预置三个 Mnemon Native 空间；「Lumen 项目」有 10 条记忆、114 条边。
2. 在 **插件 → 可组合记忆** 中打开 **Git 同步**，通过 **仓库地址** 连接裸仓库，点 **立即同步**。
3. 像把副本合并回去那样，用真实的 Mnemon CLI 把「Lumen 项目」的记忆和边重新写入它自身：`mnemon --data-dir <存储根目录> --store default import`，边的权重 0.5，备注为边的类型（[harness/rewrite-edges.py](./harness/rewrite-edges.py)）。导入跳过了全部 10 条记忆，并重新写入全部 114 条边：主键相同，值都变了。
4. 再点一次 **立即同步**，然后打开 **记忆系统 → 记忆空间**。

基线使用同一构建，只把 `src/host/space-identity.ts` 换成 main 的版本。

两个 CLI 探针用真实的 Mnemon CLI 生成同步时要合并的数据库，[harness/merge-identities.mjs](./harness/merge-identities.mjs) 分别用 main 与修复后的 `MemorySpaceIdentity` 把已发布的版本合并进本地版本：
- [harness/import-rewrites-edges.py](./harness/import-rewrites-edges.py) 像空间合并那样，把一个有三条记忆的存储导入它自身。
- [harness/embed-backfill.py](./harness/embed-backfill.py) 在没有嵌入服务响应时存入三条记忆，把这时的存储留作已发布的版本，然后对着 [harness/fake-embeddings.py](./harness/fake-embeddings.py)（在 127.0.0.1 上代替 Ollama）运行 `mnemon embed --all`，再对其中一条记忆运行 `mnemon gc --keep`。

## 自动化检查

- `tests/space-identity.spec.ts`：
  - 边只在权重、备注或时间上不同的空间，标识相同，并且两个方向上都包含对方，而同样两条记忆之间另一种类型的边是另一条边；
  - 合并这样的版本时保留本机的值，加入只有对方持有的记忆和边，所有外键完整；在一边被编辑的记忆仍会拒绝合并；
  - 之后补齐了向量、更新时间随之改变的记忆仍是同一条记忆，而遗忘仍会拒绝合并；
  - 名为 `constructor` 的表按内容比较。
- `tests/pack.spec.ts`：三轮之中，一台边被合并改写过的机器吸收另一台机器新学到的内容，始终只有一个空间，共有的边保留本机的值，并得到另一台机器的新边。
- `tests/helpers/memory-space-db.ts` 现在可以写入边的类型、权重、备注和时间。

关于边和向量的四个测试在 main 上都失败；`constructor` 测试在 main 上通过，它守护的是本次改动新增的按表查找。修复后，记忆空间与 Git 同步的测试全部通过。审查时还用真实 CLI 写入两台机器的存储，经由 `MnemonPackManager` 运行了同样的双机同步：边被改写、补齐向量、补齐向量后合并本机先前推送的版本、保留一条记忆，四种情况都只留下一个空间，而遗忘仍会保留副本。

## 限制

- 两台机器都持有某条边之后，各自保留自己的权重和备注：在一台机器上改过的值（重新关联，或在那里合并空间）只留在那台机器上，分支保存的是最后一次同步的机器的值。权重与备注只影响关联记忆的排序，任何记忆或关联都不会因此丢失。
- 合并空间时，源空间的边以权重 0.5、以边的类型为备注写入，两个空间都有的边在目标空间里因此取这些值。这来自 `mnemon_memory_body_merge`，留给单独的改动。
- 某条记忆在一边被编辑或遗忘时，仍会把另一版本保留为副本，激活状态与它所来自的空间相同，这是 #370 的设计。修复之后这条路径很少出现，但仍然没有提示：issue 建议在同步结果中报告保留了副本，留给单独的改动。
- 仍在旧版本上的机器自己还会产生这些副本；每台参与同步的机器都需要更新。
- 修复之前 main 已经产生的副本仍在原处；它们的内容是来源空间的子集，删除或合并回去都不会丢失内容。
