# Memory Spaces owns its settings and its copy

[简体中文](./README.zh-CN.md)

The Starter drew Memory Spaces' settings for it: the Provider list, the embedding settings only Mnemon Native reads and the Mnemon Native row lived in `src/client`, together with 122 entries of Memory Spaces' copy, so Memory Spaces could not change its own settings without a dsh-mnemon release. `ProviderIcon` and the Provider label helpers existed twice, and two field forms were built from the same Provider descriptor. This change gives Memory Spaces its settings and its copy, draws every Provider field with one component and keeps one settings interface whichever versions of the two packages a profile runs. Nothing a user sees or does changes: the settings, Memory Spaces' dialogs and its source lists render as on `main`, pixel for pixel and element for element, in every language DSH offers, and turning Memory Spaces on shows the same frames as on `main`. Three differences the audit found stay as they are and are planned on the roadmap ([Left for later](#left-for-later)).

Tested revision: the branch `claude/spaces-owns-settings`, merged with `main` up to #420, which moved development to DSH 0.2.1-rc.2, on 2026-10-17 with Node 24.19.0 and pnpm 10.13.1, against the pinned DSH 0.2.1-rc.2 and the installed 0.2.0-rc.2. The WebUI runs below came before that merge, on the DSH each one names.

## What changes

**Copy.** 122 keys move from `src/client/locales.ts` into Memory Spaces' `presentation/locales.json`, with their text unchanged: 40 that only its pages use (eleven `common.*` keys, `card.*` and `readSources.*`) and 82 that only its settings use (`config.provider*`, `config.embedding*`, `config.native*`, `spaces.offNote`, `common.inactive` and the rest). The Starter merges that file into its dictionaries as before, so `MnemonKey` and both dictionaries keep every key: the copy fingerprint in `tests/fixtures/presentation-baseline.json` does not move (1,341 keys in each language, the same SHA-256), because it is taken over the merged dictionaries. Memory Spaces' pages read their own copy first and then dsh-mnemon's, with the same interpolation, so every text, and a missing one, comes out as before. Three of the moved settings keys were already unused on `main` (`config.providersSpacesOn`, `config.providersSpacesOffTitle`, `config.providersSpacesOffDetail`, left by an earlier settings layout); they stay, since a public key type does not lose keys.

**Settings.** The Provider list, the embedding settings and the Mnemon Native row move into the Memory Spaces client (`src/client/settings.tsx`, `provider-settings.tsx`) with the single remaining `ProviderIcon` and Provider label helpers. Memory Spaces registers them from its own `apply()` with `installMemoryComponentUI`, as an installed component registers settings. They read the same configuration keys and call the same Host operations as before, with the same RPC names and payloads, through `host`, which the page lends them (below). They translate as dsh-mnemon drew them, through DSH's language chain and the `mnemon` namespace: their own copy answers in the first of zh and en the chain reaches, a language pack ahead of that is asked first through the namespace, and a key their copy lacks goes there too. A pack such as `ja` that falls back to English reads English, and a pack that translates the namespace is used, as on `main`.

**One field.** `ProviderField` (`src/client/provider-field.tsx`) draws every Provider field, the service fields on the configuration page and a space's fields in Memory Spaces' dialogs, in place of the two forms built from the descriptor. It shares the label, the option labels and the input attributes, and draws each place as it was drawn: the configuration page keeps its classes, its checkbox with the label beside it, its button that shows what is typed and its mask for a saved credential; the dialogs keep theirs, the label above, the note that an empty field keeps a saved credential and the choice to clear it. The two places handle a saved credential differently, and one rule for both would change what one of them shows, so each keeps its own.

**What the page lends.** Settings registered under Memory Spaces' key receive `host`; it goes with the key, not with who registered, and settings under any other key receive none. `host.configuration` reads the keys lent to Memory Spaces (`embedding`, `storageScope`, `writeEnabled`) and writes only the one it owns, `embedding`, through the page's revision-fenced settings write. `host.operations.read`/`write` call the five operations served to it (`status-summary`, `embedding-status`, `provider-services`, `embedding-fill`, `provider-service-update`) only in the page's own conversation and workspace: they refuse any other operation and any input that names a `sessionId` or `workspaceId`, so a page opened outside a conversation sends neither, as `main` did. A read Memory Spaces' settings make on their own (`provider-services`, `status-summary`) joins the same read while it is under way, but only one started at the configuration's current revision, since an older one answers for a configuration that has changed; an embedding test is never joined, since it checks the connection as it is now. `host.retained` keeps what the settings need across a remount, one store per conversation and workspace for as long as the page's client runs, and `host.changed()` has the Memory System read its pages again. As with a Source page's `management` client, neither the settings service nor the transport is handed over. Another package could get `host` only by registering under Memory Spaces' key ahead of it, which lends it nothing beyond the connection DSH already shares with every client plugin.

**For plugin authors.** `dsh-mnemon/client` adds what Memory Spaces' settings use and nothing more: `MNEMON_COMPONENT_FALLBACK_PRIORITY`, the `host` types, and the controls and styles dsh-mnemon drew those settings with, `ToggleRow`, `useLive`, `useStaged`, `PanelActions`, `WriteFailure`, `Callout`, `Reveal`, `GlobalLocationSetting` and `memorySettingsStyles`. The class map has a fixed set of keys, the 45 class names Memory Spaces' settings use: they are API, since an installed Memory Spaces older or newer than the Starter looks them up by name, and `tests/client-sidebar-css.spec.ts` keeps each of them in the style sheet. `PanelActions` and `WriteFailure` take the settings' own `t`, since the configuration page sets no translation around a component's settings. The fallback registration and Memory Spaces' installer are not exported. Exporting the constant is dsh-mnemon's promise, stated where it is declared, that it keeps those settings at that priority and lends them `host`. Nothing is removed or renamed. The [extension guide](../../en/development/extensions.md#a-components-own-settings-and-status-card) describes them.

**Client declarations stay browser-side.** Exporting the settings controls first made the declarations of `dsh-mnemon/client` reach the Host protocol through the parameter type of an internal hook, `useScope`, and with it the SDK's cordis `Context` augmentation. In a plugin's standalone install that split `Context`, and Documents' standalone typecheck in `verify:plugins` failed with `Context` errors in its tests, while `main` passed. `useScope` is now typed by the shape it reads, the client declarations are browser-side files again (21, against 17 on `main`: the four added are the exported controls), and `scripts/verify-public-entries.mjs`, part of `verify:package`, fails if they reach `src/host/` or `src/sdk/`, a cordis Context augmentation, or a package other than React and DSH's primitives.

## One settings interface whichever versions run

A profile can keep its own Memory Spaces, older or newer than the one the Starter pins. DSH keeps one entry per key and priority in a keyed region, refusing a second registration of a key at the same priority, and of a key's entries it renders the one with the lowest priority (`@deepseek-ai/dsh-client-ui-slots`, the same in 0.2.0-rc.2 and 0.2.1; DSH's `renderSlot` picks the entry the same way as `renderComponentRegion`). So:

- the Starter registers Memory Spaces' settings itself at `MNEMON_COMPONENT_FALLBACK_PRIORITY` (100). Memory Spaces' own registration, at the default priority, replaces it while it is registered, and it comes back when that one goes. The fallback therefore draws the page whenever Memory Spaces' own client registers nothing: while Memory Spaces is off, while its client loads after it is turned on, if that client fails to load or its entry fails, and beside a Memory Spaces of 0.5.21 or earlier, which has no settings of its own;
- Memory Spaces registers its own only when `dsh-mnemon/client` exports `MNEMON_COMPONENT_FALLBACK_PRIORITY`. Its client bundle is CommonJS loaded through DSH's module loader, so it reads an export the loaded dsh-mnemon lacks as `undefined`, and it reads every newer export where it draws, never when it loads. dsh-mnemon 0.5.31 registers its built-in settings at the default priority, so a registration there would be refused, and it lends no `host`.

The fallback is small: one registration of `MemorySpacesSettings`, which the Starter takes from Memory Spaces' public client entry, `dsh-mnemon-source-memory-spaces/client`, as the version it pins has it. The Starter's client build bundles every import, so it resolves that entry through the repository's TypeScript path to the pinned source (`tsdown.config.ts` names it in `alwaysBundle`). Only one module, `src/client/memory-spaces-client.ts`, imports a component's implementation; it also gives the Status page Memory Spaces' `ProviderIcon`, whose Provider list is still the Starter's. `tests/plugin-repository-boundary.spec.ts` allows that module and nothing else. A copy kept in the Starter instead would have kept the duplicated files this change removes. The fallback draws beside a Memory Spaces of 0.5.21 or earlier, so the settings Memory Spaces brings must keep working against those versions for as long as the Starter keeps it; they use the same five operations those versions answer.

One difference between versions remains, in the copy and only in languages other than zh and en: there the settings ask DSH's `mnemon` namespace first, as dsh-mnemon drew them, and that namespace holds the copy of the Memory Spaces version the Starter pins, so for a key both have, a newer Memory Spaces' own wording shows only in zh and en.

`tests/client-component-fallback.spec.tsx` builds each row in DSH's own `SlotCore` from the registration shapes each version uses: the 0.5.31 Starter registers at the default priority and its `dsh-mnemon/client` lacks `MNEMON_COMPONENT_FALLBACK_PRIORITY`, and Memory Spaces 0.5.21 registers no settings. It checks which entry DSH renders, that exactly one Memory Spaces settings interface renders, that the fallback returns when Memory Spaces' own registration goes, and that DSH refuses Memory Spaces' registration beside the 0.5.31 built-in, which is why it checks first. It also loads the built Memory Spaces client, `lib/client.js`, through `loadMemoryClientArtifact` against a `dsh-mnemon/client` with exactly the 40 export names of dsh-mnemon 0.5.31 (`tests/fixtures/dsh-mnemon-client-0.5.31-exports.json`, taken from the published bundle): its `apply()` registers its five pages and no settings, and its create dialog draws Mem0's, Hindsight's and Holographic's fields, the switch, the choice and the numbers that share the field module. `test:installed-dsh` runs the slot cases against 0.2.0-rc.2's slot core too.

The WebUI column comes from the e2e fixture with the published `dsh-mnemon@0.5.31` and `dsh-mnemon-source-memory-spaces@0.5.21` client bundles put in place of this branch's final ones (`lib/client.js` only; the Host stayed this branch's), on DSH 0.2.1-rc.2 and 0.2.0-rc.2. In each of the eight runs, the Memory Spaces page under Plugins showed one **Memory providers** heading, one Mnemon Native card and one OpenViking row, opened the OpenViking form with the same four fields, and logged no console error.

### Turning Memory Spaces on

![Turning Memory Spaces on from its page on DSH 0.2.1-rc.2: the off note, then the Providers](./switch-on.gif)

Turning Memory Spaces on from its page swaps the fallback for Memory Spaces' own settings, another implementation from another bundle, so the settings mount again. The first mount keeps the Provider list and whether the Host found the Mnemon CLI in `host.retained`; the second starts from them, and its reads join the ones still under way at the same configuration revision. `tests/client-component-fallback.spec.tsx` swaps the two in DSH's `SlotCore`, once after the first reads answered and once while they are under way: the OpenViking card and the Native card's state stay, nothing reads as loading, and the second case sends no read of its own.

Recorded in the WebUI before the last merge with `main`, on the scratch installs of DSH 0.2.1-rc.2 and 0.2.0-rc.2, English, 1280×800, for this branch and `main`: Memory Spaces turned off from its page, then on, sampling the settings on every animation frame, counting the reads the page sent, and keeping every frame Chrome painted of the settings below the component's switch.

- This branch drew the fallback's settings 85 to 93 ms after the click and Memory Spaces' own from 155 to 244 ms on; `main`, one set from 90 ms. Every sampled frame of both had the 8 Provider rows and the same Native card.
- Both sent `provider-services` and `status-summary` twice, at the first showing and once the configuration had moved, on every run; the swap added no read.
- The painted frames passed through the same states on `main` and on this branch, ending in the same frame on both releases. Two of them, the load error and the Native card's CLI state, come from two reads that answer independently, so their order varies from run to run on both: one of three runs of `main` showed the error a frame before the CLI state, as one run of this branch did.
- No console error on either.

While Memory Spaces' Source starts, the first `provider-services` read answers that the Source is not installed, and the page shows that error until the next read, on `main` as here.

## Left for later

Behavior changes are out of scope here, so these stay as on `main`; they are planned on the roadmap ([review gaps](../../plans/review-gaps-2026-10.md)):

- **A Provider without `readSources.model.<provider>` text** renders an empty line under its space in the Memory Spaces pages' source lists. Memory Spaces has the text for the nine Providers it ships with; any other Provider could read as its descriptor's label instead.
- **Two rules for a saved credential.** The configuration page fills the field with twelve dots; typing over the selected mask replaces it, but an edit that keeps part of it, such as moving the cursor and deleting one dot, saves the remaining dots as the credential. It would also show a saved credential if a Host sent one (`secretValues`; dsh-mnemon's never does). Memory Spaces' dialogs leave the field empty, say the credential is saved and kept when the field is left empty, and offer clearing it. The dialogs' rule is the safer one to settle on.
- **`.providerFieldControl` is styled twice, differently**: the configuration page's (`MnemonSettingsCard.module.css`) stacks the field at the bottom of a column and gives its checkbox no margin; the page kit's (`MnemonView.module.css`, also what Memory Spaces 0.5.21's dialogs use) is a grid whose checkbox has 2 px vertical margins. They are not copies: merging them changes where a field sits in a cell taller than it and how a checkbox is sized, so both stay.

## Compatibility

- **Profiles that pin their own Memory Spaces:** the table above. A Memory Spaces newer than this one replaces the fallback with its own settings, as this one does, and reads what the fallback kept in `host.retained` under the same names.
- **Public SDK:** additions only, listed above. The removed `MnemonClient` methods and the deleted `src/client` files were never public entries. Memory Spaces' client entry adds `MemorySpacesSettings` and `ProviderIcon`.
- **Peer floor:** Memory Spaces' settings use the new `dsh-mnemon/client` exports. It checks for them at run time and reads them where it draws, so it keeps working with an older Starter, but the release PR should raise its `dsh-mnemon` peer floor to the release that exports `MNEMON_COMPONENT_FALLBACK_PRIORITY`.
- **Stored data and Host:** no setting, key, RPC name, payload or tool changes; the Host is untouched. `tests/client-component-host.spec.ts` checks the RPC names and payloads the moved settings send, the page-bound scope, which reads are joined and the retained store; `tests/client-component-reads.spec.tsx` checks that a test or a Provider list made after a configuration change asks the Host again and shows its answer.
- **Styles:** no style rule changes. The moved settings use the configuration's class map from `dsh-mnemon/client`, so the Starter still owns those rules, and the dialogs keep the page kit's.
- **Copy:** an older Starter beside this Memory Spaces still has every key in its own dictionary; Memory Spaces reads its own copy first, through DSH's language chain in its settings.
