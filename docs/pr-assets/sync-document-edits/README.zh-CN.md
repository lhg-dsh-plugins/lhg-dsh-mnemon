# 通过 Git 同步传递项目档案的修改

[English](./README.md) | [验证记录](./verification.json)

这个问题是在通过 Git 同步核对 issue #370 的记忆空间修复时发现的。每次推送前都会先把分支合并到本机，而分支上保存的仍是每份档案上次发布的版本，于是编辑过的档案会遇到同一 id 下自己的旧版本，合并把这个旧版本当作副本保留了下来：
- 在一台机器上编辑两次、同步三次，最后有三份档案；
- 在两台机器之间，一边的修改永远不会更新另一边的同一份档案，而是又多出一份副本。

基线：main `20e4ab67`。修复：`6a0eb318`。运行于 2026-10-13（Asia/Shanghai）：
- macOS 15.6 arm64，Node 24.19.0；
- headless Chrome，1280×900，zh-CN，浅色；
- DSH 0.2.1-alpha.2（npm `alpha`），通过 `scripts/serve-e2e.mjs` 运行；
- 本机裸仓库通过 Git 的 `url.<base>.insteadOf` 代替 `https://git.example.com/demo/memory.git`。

## 修复

每次合并和每次发布之后，设备会记下它与分支此时一致的每份档案的版本，以及达成一致时的提交。这份记录保存在 `state/sync/base.json`，按仓库、分支和目录区分。版本包括档案的所有字段，只有上次读取的时间除外，所以重命名和归档都算改动。

此后通过同步通道合并时，两边都有的每份档案都和这份记录比较：

| 分支上的版本 | 本机的版本 | 结果 |
|---|---|---|
| 未改动 | 改动或未改动 | 保留本机的版本 |
| 改动过 | 未改动 | 用分支上的版本替换本机的，分支的修订号比本机低时除外 |
| 改动过 | 改动过 | 本机的版本保留原 id，修订号高于两边；分支的版本作为副本保留在旁边，即使只有标题或归档状态不同 |

这份记录在合并之后就立即写下，而不是只在发布之后写。因此，即使推送被 Git 拒绝或失败，或者这台设备根本不能发布，下次比较的仍是它已经合并进来的版本。

只有分支仍从达成一致时的提交（即镜像检出的提交）延续下来，这份记录才会被使用。分支被删除后又从较旧的历史重新发布时，会像以前一样保留副本，不会丢失任何文本。断开连接不会删除这份记录，重新连接同一个仓库后会继续使用。

ZIP 导入没有这份记录，合并方式和以前一样。升级后的第一次同步，以及换到另一个仓库、分支或目录后的第一次同步，也是如此。

这个修复的早期版本先后经过两轮独立审查，审查发现的每种情况现在都是下面的一个场景：
- 推送被拒或发布失败；
- 不能发布的设备；
- 被重建的分支；
- 另一台设备上较旧的 dsh-mnemon；
- 重命名或归档；
- 修订号不同的冲突；
- 对同一正文一边归档、一边重命名；
- 断开连接。

## 方法

**一台机器。**
1. 启动 WebUI，打开 **Git 同步** 并连接。
2. 在 **记忆系统 → 项目档案** 中新建 **Release plan**，点击 **立即同步**。
3. 编辑两次，每次编辑后点击 **立即同步**。

**两台机器。**
1. Studio 新建 **Release plan** 并同步。
2. MacBook 连接同一个仓库并同步，带入这份档案。
3. Studio 把它编辑为第 2 版并同步。
4. MacBook 再同步一次，然后打开 **项目档案** 并点击 **刷新**。

## 场景

`tests/git-sync.spec.ts` 在真实的裸仓库上运行每个场景，`tests/pack.spec.ts` 另用七个测试直接检查合并规则。下表比较 main、修复的第一个版本（`0eef4f6f`）和当前版本：

| 场景 | main | `0eef4f6f` | 修复 |
|---|---|---|---|
| 一台机器在两次同步之间编辑 | 失败 | 通过 | 通过 |
| 一台机器的修改到达另一台 | 失败 | 通过 | 通过 |
| 两台机器都编辑：只有一份副本，两边结果一致 | 失败 | 通过 | 通过 |
| 另一台机器同时发布后重试 | 失败 | 失败 | 通过 |
| 合并后没能发布，之后追上分支 | 失败 | 失败 | 通过 |
| 在没能发布的合并之上编辑 | 失败 | 失败 | 通过 |
| 能读取分支、但永远不能发布的机器 | 失败 | 失败 | 通过 |
| 分支从较旧的历史重新发布，较新的文本保留 | 通过 | 失败（文本丢失） | 通过 |
| 另一台机器运行较旧的 dsh-mnemon，较新的文本保留 | 通过 | 失败 | 通过 |
| 另一台机器改了正文时，重命名和归档保留 | 失败 | 失败 | 通过 |
| 一台机器改的标题到达另一台 | 失败 | 失败 | 通过 |
| 只合并到本机之后的一致记录 | 失败 | 通过 | 通过 |
| 只合并运行时记忆时，一致记录不变 | 失败 | 通过 | 通过 |
| 无法读取的一致记录，然后断开并重新连接 | 失败 | 失败 | 通过 |
| 两台机器以不同的修订号编辑，两边结果一致 | 失败 | 通过 | 通过 |
| 同一正文，一台机器归档、另一台重命名 | 失败 | 失败 | 通过 |
| 一台机器的归档到达另一台 | 失败 | 失败 | 通过 |
| 不会使用另一个分支的一致记录 | 通过 | 通过 | 通过 |

在 main 上通过的场景是安全性场景：main 把所有不同都保留为副本，所以从不丢失文本。修复在无法确定时同样保留副本。如果去掉「只合并到本机」之后写入一致记录的那一步，对应的测试就会失败。

## 限制

- 运行较旧 dsh-mnemon 的设备仍会产生副本，每台参与同步的设备都应更新。
- 在产品之外删除的档案会从分支上恢复回来，与 main 一样。产品本身只会归档档案。
- 早期版本已经产生的副本会保留。这个修复只阻止新的副本，不会合并或删除已有的副本。
- 在分支或目录之间来回切换时，每次都从没有一致记录开始，所以切换后的第一次同步会保留副本。
