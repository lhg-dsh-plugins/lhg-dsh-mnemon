# v0.5.32：更清楚的存入回执与记忆空间自带设置

**简体中文** | [English](../../en/releases/v0.5.32.md)

本补丁版本发布 v0.5.31 之后那次审查的后续改动：[#414](https://github.com/omdsh-dev/dsh-mnemon/pull/414) 至 [#430](https://github.com/omdsh-dev/dsh-mnemon/pull/430)。其中一项改动用户可以看到；其余改动保持用户与模型看到的内容不变，由各组件接管自己的部分，并把代码拆成更小的模块。

- **未生成向量的存入改为说明性提示**（#427）。在没有嵌入服务的安装中，存入记忆空间的回执末尾以前都会出现一行橙色警示（“未生成向量：嵌入没有成功……”），看起来像是出了故障。现在，DSH 不管理 Mnemon Native 嵌入设置时（默认如此），对话中与记忆空间页面上的存入记忆回执，以及 `/mnemon remember`，末尾改为中性的说明：当前没有可用的嵌入服务，关键词检索不受影响，连接嵌入服务后可在**测试状态**中补齐向量。DSH 管理嵌入设置时，服务没有响应仍保留原有警示，一字不改。模型读到的内容不变。
- **记忆空间自带设置**（#421）。Provider、Mnemon Native 读取的嵌入设置及其文案改由记忆空间包提供，记忆空间因此可以不随 dsh-mnemon 发布就修改它们。它们在 DSH 提供的每种语言中的外观与行为都与之前相同。记忆空间自己的客户端没有注册设置时，由 dsh-mnemon 保留的同一套设置作为后备，因此无论 Profile 运行哪些版本，都只显示一套。
- **文档。** 快速开始现在从记忆系统讲起，命令行安装、Headless 与云端访问移至安装与启动，每个主题只保留一处完整说明（#415）。截图与录屏来自新图集：在 DSH 0.2.1-rc.2 上由真实 DeepSeek 模型作答、使用本地嵌入服务，中英文各一套（#424、#429）。路线图与设计计划列出审查发现的 23 项功能性改动，每项写明现状、改法与测试；本版本发布其中一项，即中性提示（#417、#422、#430）。
- **DSH 0.2.1-rc.2**（#420）。开发与 CI 改用新的 npm `next`，即 DSH 0.2.1-rc.2，本版本在其上验证；支持范围不变。
- **面向插件作者。**
  - 策略在 manifest 的 `workflows` 字段中声明 dsh-mnemon 为其回合运行的后台工作：`idle-review` 与 `runtime-capacity`，第三方策略也可以选用其中任一项。展开分层策略 manifest 构建的策略现在也会继承 `workflows`，`workflows: []` 让它两项都不参与；`threeTierActionWorkflow` 仍然导出，但已弃用（#414）。
  - 每个 Source 的 `./contracts` 入口给出自己的文件名，并导出读取这些文件的规则，备份、Git 同步与存储清单都改用它们（#416）；记忆空间新增仅限 Node 的 `./space-identity` 入口。
  - 记忆空间的 `./contracts` 导出 `NATIVE_PROVIDER_ID`、`isNativeProvider()`、空间名称与描述的长度上限（`MEMORY_SPACE_NAME_MAX_LENGTH`、`MEMORY_SPACE_DESCRIPTION_MAX_LENGTH`）以及 `MEMORY_PLACEMENT_CAPABILITIES`，其 `MemorySpacesStatus` 新增可选的 `embeddingManaged`；它的 `./client` 入口新增 `MemorySpacesSettings`、`ProviderIcon` 与 `NATIVE_PROVIDER_ID`。运行时记忆的 `./contracts` 导出 `RUNTIME_MEMORY_LIMIT_MAX_BYTES`（#421、#423、#426、#427）。
  - `dsh-mnemon/client` 新增 `MNEMON_COMPONENT_FALLBACK_PRIORITY`、组件设置拿到的 `MemoryComponentHost`，以及绘制记忆空间设置所用的控件与 class 映射（#421）；`WriteReceipt` 新增可选的 `embeddingManaged`，用来选择提示措辞（#427）。
  - 开发指南新增兼容性登记表，列出每段兼容代码及其可以移除的条件（#423）。
- **维护。** 记忆工具的各项事实集中到一张表（#418）；常量、通信类型、Host 的端点列表与 Git 同步检查各自只有一个归属（#426）；最大的 Host 与客户端模块按已有接缝拆分，并用测试固定每个记忆任务的指令与模型看到的每个工具（#425、#428）；只存在于 PR 记录中的测试工具移入测试与脚本（#419）。

## 升级与兼容性

**DSH 0.2.0-rc.2、0.2.1-rc.1 与 0.2.1-rc.2：** 使用**记忆系统 → 状态 → 检查版本 → 更新**，完成后重启 DSH。在 DSH 0.2.0-rc.2 上，较早的版本也可以这样更新；在 DSH 0.2.1 上，需要 dsh-mnemon 0.5.31 或更高版本。在 DSH 0.2.1 上使用 dsh-mnemon 0.5.30 或更早版本时，更新会停在 `already-installed`：请退出 DSH，安装一次精确版本，再启动 DSH。

```sh
dsh plugin --profile web add dsh-mnemon@0.5.32
```

写明版本，可以避免 pnpm 在新版本发布后的 24 小时内选用较早的版本。命令行不管理桌面版的 `desktop` profile：在桌面版中，请在插件页**卸载** dsh-mnemon，再通过**添加插件**以 `dsh-mnemon@0.5.32` 重新安装，然后完全退出并重新打开应用。记忆数据与设置都会保留。

**支持的 DSH 版本**不变：DSH 0.2.0-rc.2 与 0.2.1-rc.1，以及此后的 0.2.0 与更高的 0.2 版本（`>=0.2.0-rc.2 <0.2.1-0 || >=0.2.1-rc.1 <0.3.0-0`），其中包括 0.2.1-rc.2。DSH 0.1.7、0.2.0-rc.1 与 0.2.1 的 alpha 版本会拒绝安装本版本：

- 在 DSH 0.1.7-rc.2、0.2.0-rc.1 或 0.2.1-alpha.2 上，升级 DSH 之前请保留 dsh-mnemon 0.5.30，见[升级顺序](../reference/compatibility.md#升级顺序)。
- 在 DSH 0.2.1-alpha.3 及之后的 alpha 版本上，没有完全可用的版本。请把 DSH 升级到 0.2.1-rc.2，再按上文安装 0.5.32。

如果 Profile 独立维护了本版本改动的组件，请同时更新这些副本（版本见下表），或移除它们，改用 Starter 自带的副本；Starter 会自动锁定新版本。与较早的 Starter 一起使用的记忆空间 0.5.22 会沿用那个 Starter 绘制的设置；与本 Starter 一起使用的记忆空间 0.5.21 及更早版本，会得到本 Starter 的后备设置。记忆空间 0.5.21 或更早版本与本 Starter 一起使用时，未生成向量的存入在记忆空间页面上仍显示原有警示，对话与 `/mnemon remember` 显示中性说明；记忆空间 0.5.22 与较早的 Starter 一起使用时，各处都保留原有警示。尚未声明 `workflows` 的分层策略仍会驱动空闲审查与运行时容量维护。

已有记忆与设置无需迁移，已保存的设置键不变。仍保存着 `conversationInteraction.toolviews` 偏好（自 0.1.3 起已不起作用）的 profile 照常加载，解析后的配置不再包含它。完整 profile 使用 Node `^22.19.0 || >=24.0.0`。插件的 peer 下限与 Starter 的外部运行时依赖不变。
